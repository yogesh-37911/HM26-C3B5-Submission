# Known Limitations

Written honestly, as required. This is an initial CivicPulse MVP, not a
production civic system.

1. **Synthetic demo dataset.** All 500+ complaints, the 65-ward city
   geography, sensitive-place list (schools/hospitals), and complaint
   phrasing are generated by `src/scripts/seed.py`. None of it is real MCC
   data, and no statistic derived from it describes real Mysuru. This is
   labelled on every relevant API response and dashboard screen.

2. **Jurisdiction boundaries are demonstration geometry.** Ward polygons are
   procedurally generated hexagons around approximate locality centre points,
   not surveyed GIS boundaries. The *mechanism* (versioned boundaries,
   immutable historical routing) is production-grade; the *geometry* is not.
   A real deployment needs authoritative MCC/Survey of India shapefiles
   imported into the same `jurisdiction_versions` table.

3. **The neglect-risk and priority models are unvalidated heuristics**, not
   trained ML. We chose an interpretable additive scoring model over a
   black-box classifier because the MVP has no real historical municipal
   outcome data to train or calibrate against, and a civic officer acting on
   a prioritisation needs to see why. The weights (e.g. "inactivity is worth
   up to 26 of 100 risk points") are reasoned defaults, not fitted
   coefficients. Once real resolution-time data exists, the same
   `compute_risk(...) -> score/level/factors/action` interface can be
   backed by a trained logistic regression or random forest without
   changing any caller.

4. **No guarantee verification detects fraudulent reports.** The scoring
   pipeline raises the bar for a determined bad actor; it does not defeat
   one. A well-crafted fake report with a plausible description and a fresh
   photo can still score `PLAUSIBLE`.

5. **Map accuracy depends on available GIS data.** Duplicate detection and
   jurisdiction routing use bounding-box + Haversine distance on raw
   lat/lng rather than PostGIS. This is accurate enough at city scale
   (error is sub-metre at Mysuru's latitude for the distances involved) but
   does not account for terrain, or for boundaries that aren't well
   approximated by a simple polygon.

6. **Offline sync is MVP-level.** The client queues actions with an
   idempotency key and replays them on reconnect; there is no conflict
   resolution beyond "first write wins" and no background sync while the
   app is closed (a full offline-first PWA with a service worker is future
   work).

7. **Real MCC deployment requires integration with official systems** -
   citizen SSO, an authoritative ward GIS layer, an actual SMS/notification
   gateway, and a real image-storage/CDN layer in place of local disk
   storage.

8. **Single-server demo topology.** The Dasara surge simulation demonstrates
   the *concept* of asynchronous batch processing (a background task,
   polled status, no UI freeze) but runs in-process rather than on a real
   message queue (SQS/Kafka) or worker pool, which a 50,000/day sustained
   load would require.

## Roadmap

**Phase 2**
- Import authoritative ward boundary GIS data.
- Replace the deterministic risk/priority weights with a model calibrated
  on real resolution-time data, keeping the same explainable-factor output
  contract.
- Real push notifications (SMS/WhatsApp) alongside in-app notifications.

**Phase 3**
- Full offline-first PWA (service worker, background sync).
- Citizen-facing OTP/SSO login.
- Queue-based (SQS/Kafka) ingestion for genuine surge load, with the surge
  simulator becoming a load-test harness against the real queue.

**Production**
- PostGIS for boundary and proximity queries at scale.
- Object storage (S3-compatible) + CDN for evidence photos.
- Audit-log retention policy and a proper admin review workflow for
  `SUSPICIOUS` reports.
- Formal integration with MCC's existing grievance/works-order systems
  rather than operating as a standalone platform.
